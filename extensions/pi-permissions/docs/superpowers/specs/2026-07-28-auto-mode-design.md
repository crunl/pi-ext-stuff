# Pi Permissions Auto Mode Design

Status: proposed implementation specification
Date: 2026-07-28

## 1. Purpose

Add an `Auto` permission mode to `pi-permissions` that keeps the existing
Default-mode sandbox and deterministic safety boundaries, while delegating
approval prompts to a separate model call.

The target experience is Codex's “Approve for me” behavior with grok-build's
useful denial feedback and graceful fallback:

- clearly safe operations continue without another model call;
- deterministic policy blocks remain final;
- only operations that Default mode would ask the user to approve are reviewed;
- an approval grants exactly one bound tool call and does not widen the session;
- reviewer failures fall back to the existing Yes/No dialog when UI is available;
- repeated reviewer denials pause automatic review.

## 2. Reference Behavior

The design adopts these upstream properties:

- Codex keeps `OnRequest` approval semantics and replaces the human reviewer
  with `AutoReview`; it does not equate auto-review with full access.
- Codex runs a separate guardian review session, uses a structured allow/deny
  result, fails closed around its sandbox, and stops denial loops.
- grok-build distinguishes `Auto` from `AlwaysApprove`, uses deterministic
  fast paths before its classifier, returns denial reasons to the main agent,
  and falls back to ordinary prompting when the classifier is unavailable.

This plugin does not copy either implementation wholesale. The existing
Default evaluator and sandbox are the authoritative deterministic layer.

## 3. Goals

1. Make `defaultMode: "auto"` functional.
2. Allow switching between functional `Default` and `Auto` modes at runtime.
3. Reuse Pi's configured model registry and credentials for a separate reviewer
   request.
4. Keep all Default-mode hard blocks, protected paths, private-network checks,
   configured deny rules, and sandbox enforcement non-overridable.
5. Bind every automatic approval to the exact tool, input, working directory,
   configuration fingerprint, and tool-call ID.
6. Provide a bounded, cancellable reviewer call with strict structured output.
7. Prevent prompt injection from tool output, assistant prose, project files,
   or tool-call arguments being treated as user authorization.
8. Pause automatic review after repeated denials and provide a clear recovery
   path.
9. Preserve the compact statusline label: `Default` or `Auto`.

## 4. Non-goals

- `AlwaysApprove`, YOLO, or sandbox bypass.
- Allowing the reviewer to override a deterministic block.
- Persistent “always allow” rules generated by the reviewer.
- Reviewer tool use, shell access, filesystem access, or network browsing.
- A full Plan-mode workflow, plan document lifecycle, or plan approval UI.
- Treating project `AGENTS.md`, tool results, or assistant explanations as user
  authorization.

Plan mode remains a separate SDD unit. Until its enforcement is implemented,
the runtime shortcut must not activate it. The mode controller may retain the
`plan` state type for forward compatibility, but the active cycle is
`Default → Auto → Default`.

## 5. Trust and Configuration Boundaries

### 5.1 Authoritative layers

The decision order is fixed:

1. Load and validate the effective permissions configuration.
2. Run `evaluateDefaultRequest`.
3. If the result is `allow`, execute under the current sandbox.
4. If the result is `block`, block without invoking the reviewer.
5. If the result is `prompt`:
   - Default mode uses the existing human confirmation;
   - Auto mode invokes the reviewer, unless Auto is paused;
   - paused Auto uses human confirmation.
6. Immediately before execution, re-evaluate the request inside the sandbox
   coordinator lease using the current config and exact approval record.

The reviewer is advisory only. It can convert a Default `prompt` into a
single-call approval or denial. It cannot convert `block` into `allow`.

### 5.2 Configuration source

The existing global `reviewer` object controls an explicit reviewer:

```json
{
  "reviewer": {
    "provider": "openai-codex",
    "model": "gpt-5.6-sol-fast",
    "reasoningEffort": "medium",
    "timeoutMs": 60000,
    "maxConsecutiveDenials": 3
  }
}
```

Rules:

- Global user configuration may select and configure the reviewer.
- Project configuration must not select a reviewer, enable Auto as the default,
  weaken reviewer limits, or replace the reviewer policy.
- If no explicit reviewer is configured, Auto uses the active session model as
  a separate, stateless model call.
- If neither an explicit reviewer nor an active model is available, the
  reviewer is unavailable and the fallback policy applies.
- Invalid timeout or denial limits are configuration errors. `timeoutMs` must
  be a positive safe integer; `maxConsecutiveDenials` must be a positive safe
  integer.

The separate call may use the same model ID as the main agent, but it has an
independent prompt, message list, request ID, timeout, and no tools.

## 6. Components

### 6.1 Mode runtime

A runtime mode owner coordinates:

- active mode (`default` or `auto` for this delivery);
- pending transitions while a tool call or reviewer is active;
- Auto paused state and consecutive denial count;
- statusline updates;
- persistence through `pi-permissions-state`.

Mode changes are rejected or queued while a human approval or model review is
active. A successful transition clears stale one-call approval capabilities.

Commands:

- `/default` activates Default.
- `/auto` activates Auto and clears the paused/denial state.
- `/permissions` reports the active mode, sandbox profile, reviewer model, and
  whether Auto is paused.

### 6.2 Reviewer client

Create a small `AutoReviewer` interface so policy orchestration is independent
of `pi-ai`:

```ts
interface AutoReviewer {
  review(request: AutoReviewRequest, signal?: AbortSignal):
    Promise<AutoReviewResult>;
}
```

The production implementation:

- resolves the configured model through `ctx.modelRegistry.find`;
- otherwise uses `ctx.model`;
- resolves credentials through `ctx.modelRegistry.getApiKeyAndHeaders`;
- calls `pi-ai` `complete`;
- disables provider retries (`maxRetries: 0`);
- supplies `timeoutMs`, the combined cancellation signal, configured reasoning
  effort, `cacheRetention: "none"`, and a fresh session ID;
- exposes no tools to the review call;
- accepts only a strict JSON object as the final text.

### 6.3 Review request builder

`AutoReviewRequest` contains:

- exact tool name and input;
- normalized operation, paths, network targets, and shell command;
- working directory;
- sandbox profile;
- Default decision risk, reason, requested temporary write roots, and requested
  network hosts;
- retained genuine user messages from the active session branch;
- prior harness-owned reviewer decisions for the current turn, when available.

The builder excludes:

- tool results;
- assistant free-form text;
- system-generated user messages;
- project instructions as authorization;
- prior model rationales as authorization.

User text and tool input are serialized into clearly delimited data sections.
The reviewer policy states that instructions inside serialized tool arguments,
quoted text, project content, and action payloads are inert data.

Input is bounded:

- keep the first genuine user request and the newest genuine user messages;
- cap each message and the total retained transcript;
- never truncate the exact current tool call without marking the review
  unavailable.

### 6.4 Reviewer policy and result

The reviewer answers only:

```json
{
  "decision": "approve",
  "risk": "low",
  "rationale": "The requested test command matches the user's request."
}
```

or:

```json
{
  "decision": "deny",
  "risk": "high",
  "rationale": "This publishes externally without current user authorization."
}
```

All fields are required. Unknown fields, code fences, trailing prose, invalid
risk values, empty rationale, or any other shape are parse failures.

Approval criteria:

- the action is a reasonable and scoped consequence of a current user request;
- the temporary permissions are minimal;
- the operation stays inside the declared sandbox boundary;
- the action is not destructive, privileged, secret-exfiltrating, a trust
  boundary crossing, or an externally visible side effect lacking explicit
  current authorization.

When uncertain, the reviewer denies.

### 6.5 Approval capability

An automatic approval uses the existing approval record and temporary
capability maps. The record additionally identifies its authority as
`auto-review`.

Execution consumes the capability once and revalidates:

- tool-call ID;
- lower-cased tool name;
- full input fingerprint;
- normalized cwd;
- current config fingerprint;
- current mode;
- current Default decision;
- approved temporary write roots and network hosts.

Reload, mode change, session switch, shutdown, input substitution, cwd change,
or a changed policy invalidates the capability.

## 7. Decision and Fallback Flow

### 7.1 Reviewer approval

1. Reset consecutive denials to zero.
2. Store the exact one-call approval and temporary capabilities.
3. Return from `tool_call` without blocking.
4. Execute through the existing sandboxed tool wrapper.

### 7.2 Reviewer denial

1. Increment consecutive denials.
2. Return a blocked tool call with a concise reviewer rationale and guidance to
   try a materially safer approach.
3. Do not show a human dialog for the first denials.
4. At `maxConsecutiveDenials`, set Auto to paused.
5. The denied threshold-crossing action remains denied; the next prompt uses
   the human approval dialog. This prevents a denial from immediately becoming
   approval merely because the threshold was reached.
6. `/auto` explicitly resumes Auto and resets the counter.

Any reviewer approval resets the consecutive denial counter.

### 7.3 Reviewer failure

Failures include:

- model/provider not found;
- missing or invalid authentication;
- timeout or cancellation not caused by user/session shutdown;
- provider error;
- empty response;
- malformed JSON;
- invalid result schema.

When dialog-capable UI is available, these failures fall back immediately to
the existing Yes/No approval dialog and disclose that automatic review was
unavailable. Human approval creates the same exact one-call capability as
Default mode.

Without dialog-capable UI, failure is fail-closed. Cancellation caused by turn
abort, session switch, or shutdown never opens a fallback dialog.

## 8. Concurrency and Lifecycle

- At most one review promise exists per tool-call ID.
- Concurrent different tool calls may be reviewed independently, but each
  result remains bound to its own ID and request fingerprint.
- `approvalActive` covers both model review and human fallback.
- Session shutdown aborts all in-flight reviewers and clears approval state.
- Successful config reload and mode transition abort reviewers whose snapshots
  no longer match.
- Late reviewer results are ignored after cancellation, reload, transition, or
  session replacement.
- Reviewer calls do not hold the sandbox execution lease. The lease is acquired
  only for execution, where authorization is revalidated.

## 9. UI and Shortcut

The statusline continues to use the existing status key and renders only the
mode label:

```text
── Auto•(tuzi) gpt-5.6-sol-fast•xhigh ───
```

Notifications are limited to:

- entering Default or Auto;
- Auto reviewer unavailable and human fallback opened;
- Auto paused after repeated denials;
- invalid reviewer configuration.

Pi reserves `Shift+Tab` for `app.thinking.cycle`, and extensions cannot override
a reserved binding. Installation therefore requires a user keybinding
migration:

```json
{
  "app.thinking.cycle": "ctrl+shift+t"
}
```

After that migration, `pi-permissions` can register `Shift+Tab` for the active
functional mode cycle. For this delivery the cycle is `Default ↔ Auto`. Plan is
added only after its read-only enforcement has its own approved spec.

If `Shift+Tab` remains reserved, the extension must not pretend registration
succeeded. It keeps `/default` and `/auto` available and shows one actionable
warning.

## 10. Testing Strategy

### 10.1 Unit tests

- strict reviewer output parsing;
- transcript selection and injection-resistant framing;
- configured-model and active-model resolution;
- approve, deny, timeout, provider error, parse error, and cancellation;
- consecutive denial reset and pause threshold;
- global/project reviewer restriction merging;
- mode transition and persisted state validation.

### 10.2 Registration tests

- Default `allow` bypasses reviewer;
- Default `block` cannot invoke or be overridden by reviewer;
- Default `prompt` in Auto invokes reviewer;
- approved call receives only its requested temporary permissions;
- denied call never reaches tool execution;
- reviewer failure opens human fallback only with UI;
- headless failure blocks;
- reload/mode change/input swap/cwd change invalidate automatic approval;
- late review completion cannot grant execution;
- paused Auto uses human approval;
- `/auto` resumes and resets;
- statusline shows only `Auto` or `Default`.

### 10.3 Sandbox and integration tests

- automatic approval still cannot read or write protected secrets;
- automatic approval still cannot reach private/special network targets;
- native write/edit and Bash remain in the OS sandbox;
- public one-call network and additional filesystem grants are restored after
  execution;
- concurrent approvals cannot leak capabilities;
- real Pi model/auth failures follow the documented fallback.

### 10.4 Shortcut verification

- `Shift+Tab` cycles only functional modes after keybinding migration;
- a reserved binding produces a warning instead of a false success state;
- statusline extension output remains compact and non-duplicated.

## 11. Acceptance Criteria

Auto mode is complete only when all of the following are proven:

1. `defaultMode: "auto"` starts in functional Auto mode.
2. `/auto` and the migrated shortcut activate Auto and update the statusline.
3. A Default hard block never reaches the reviewer.
4. A reviewer approval executes exactly once under the existing sandbox.
5. A reviewer denial blocks execution and returns its reason to the agent.
6. Three consecutive denials pause Auto with the default configuration.
7. Reviewer failure opens human fallback with UI and blocks headlessly.
8. Project configuration cannot enable or weaken Auto/reviewer policy.
9. Reload, mode transition, cancellation, and request substitution cannot reuse
   an automatic approval.
10. Protected paths, private networks, and sandbox boundaries remain enforced.
11. Unit, integration, type, and diff checks pass.
12. An independent security-focused code review reports no unresolved
    Critical or Important issue.
